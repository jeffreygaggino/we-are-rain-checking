# 03 — The gate in CI

Implements #21. `02-scope-reset.md` §Pipeline owns the shape of the pipeline and the reasons for it —
one gate job rather than parallel lint/test, Postgres from compose rather than a `services:` block,
branch protection as the part that matters. This plan holds only what 02 left to the build: how the
workflow invokes the gate, and how the required check gets seen refusing a merge.

Release and deploy are #22 and are not in this file.

## The workflow

`.github/workflows/ci.yml`, one job, `gate`, on pull requests targeting `main` and pushes to `main`.

**The job invokes `make gate`.** Not `go vet` then `swag init` then `go build` then `go test` as four
steps. Those four are already named in one place, the Makefile; naming them again in YAML is a second
definition of "verified" that drifts the moment someone edits one and not the other — the failure the
deleted drift exhibit was about, aimed at ourselves. Every step in the workflow that is not
`make gate` exists to make `make gate` runnable: check out the code, install Go, install `swag`.

**Go is pinned by `go-version-file: backend/go.mod`,** not by a version literal in the YAML. A literal
is the same duplication one layer up: `go.mod` already says `1.27.0`, and a workflow that repeats it
floats away from the module the first time the module is bumped.

**`swag` is pinned the same way.** `make docs-check` requires the binary and refuses to guess, so CI
installs it — at the version `go.mod` already resolves for the library:

```
go install github.com/swaggo/swag/cmd/swag@$(go list -m -f '{{.Version}}' github.com/swaggo/swag)
```

`@latest` would mean a spec regenerated by a tool no local run uses.

**No path filters.** A required check that is skipped on a documentation-only pull request never
reports, and a required check that never reports blocks the merge forever. The gate is cheap; it runs
on everything.

**Concurrency is keyed on the ref, cancelling in progress on pull requests only.** A superseded pull
request run is wasted minutes; a superseded push to `main` is a lost record of whether `main` was ever
green at that commit.

### Rejected

| | why not |
|---|---|
| `services: postgres` | 02 §Pipeline: unreachable through `docker compose exec`, so `make test-db` would have to be rewritten for CI. Runners have Docker. |
| Separate `lint` and `test` jobs | 02 §Pipeline: an optimisation on a build measured at nothing, and two checks to keep in the protection rule instead of one. |
| A `swag` version literal in the YAML | drifts from `go.mod`. |
| Dumping the Postgres container logs on failure | the gate's own output already says what failed. Add it the first time a CI failure is genuinely unreadable without it, not before. |

## Seeing it refuse a merge

The last acceptance criterion is the one that cannot be satisfied by reading the YAML. A protection
rule that has never blocked anything is an assumption, and this repo's principle is that a result is
not trusted until it has been seen to fail. So, in order, after this branch merges:

1. **Merge this branch.** The check must exist on `main` before it can be required — a rule naming a
   check that has never run blocks every merge, including the one that would fix it.
2. **Protect `main`,** requiring the `gate` check and a pull request:

   ```
   gh api --method PUT repos/jeffreygaggino/we-are-rain-checking/branches/main/protection \
     --input - <<'JSON'
   {
     "required_status_checks": { "strict": true, "contexts": ["gate"] },
     "enforce_admins": true,
     "required_pull_request_reviews": null,
     "restrictions": null
   }
   JSON
   ```

   `enforce_admins: true` on a single-maintainer repo is the whole point: without it the rule is
   advisory to the only person who can merge. `required_pull_request_reviews: null` because there is
   nobody else to review; the gate is the reviewer this rule is enforcing.

3. **Break it on purpose.** Branch, commit something the gate genuinely rejects — a `t.Fatal` in a
   passing test, or a line of misformatted Go — and open a pull request.
4. **Watch the merge be refused.** `gh pr checks <n>` red, and the merge button blocked rather than
   merely discouraged. `gh pr merge <n>` should refuse.
5. **Revert the breaking commit on that branch,** watch the check go green, and confirm the merge is
   then allowed. The branch merges with the break reverted, not with it in the tree.

Step 3 through 5 is the evidence. Without it #21 has produced a green badge over an unprotected main,
which is decoration.
